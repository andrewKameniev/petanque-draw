## Critical / High — Real Bugs

### 1. Crash on empty tournaments

- **File:** `src/stores/main.js:909`
- **Severity:** Critical
- **Code:**
  ```js
  this.setActiveTournament(
    this.tournaments[Object.keys(this.tournaments)[Object.keys(this.tournaments).length - 1]].id,
  );
  ```
- **Issue:** Accesses `.id` on `undefined` when no owned tournaments remain after the pinned/shared fallthrough logic.
- **Scenario:** User has only shared tournaments (role != owner) and the pinned ID no longer matches any owned tournament. The else branch is reached with an empty `this.tournaments` object.

### 2. String comparison in playoff winner determination

- **File:** `src/helpers.js:77`
- **Severity:** High
- **Code:**
  ```js
  playOffList[i].teams[0].team_1_score > playOffList[i].teams[0].team_2_score
    ? playOffList[i].teams[0].team_1
    : playOffList[i].teams[0].team_2;
  ```
- **Issue:** No `Number()` coercion. Firebase can store scores as strings. `'9' > '13'` is `true` lexicographically.
- **Scenario:** A playoff final has scores stored as strings — the wrong team is declared champion.

### 3. String concatenation in score accumulation

- **File:** `src/services/draw.js:1148`
- **Severity:** High
- **Code:**
  ```js
  firstTeam.pointsPlus += game.team_1_score;
  firstTeam.pointsMinus += game.team_2_score;
  ```
- **Issue:** If score is a string from Firebase, `0 + '13' = '013'` (string concatenation).
- **Scenario:** After any recalculation with string scores, all rankings become nonsensical.

### 4. Fractional group count in poules

- **File:** `src/services/draw.js:939`
- **Severity:** High
- **Code:**
  ```js
  const groupsQuantity = teamsCount / 4;
  ```
- **Issue:** No `Math.ceil`/`Math.floor`/rounding. 10 teams = 2.5 groups.
- **Scenario:** Organizer starts poules with 10 teams. Loop creates only 2 groups, silently dropping teams from the draw.

### 5. Poules round 2 assumes exactly 2 games per group

- **File:** `src/services/draw.js:993`
- **Severity:** High
- **Code:**
  ```js
  const r1Games = tournament.games[tournament.games.length - 1].filter((g) => g.group === groupIndex);
  const game1 = r1Games[0];
  const game2 = r1Games[1];
  const winner1 = game1.team_1_score > game1.team_2_score ? game1.team_1 : game1.team_2;
  ```
- **Issue:** If a group has <4 teams, `r1Games[1]` is `undefined` → crash on `.team_1_score`.
- **Scenario:** A poules group with 3 teams (odd total) or deleted/corrupted games.

### 6. Crash on old tournaments without preferences

- **File:** `src/components/partials/Results.vue:126, 520`
- **Severity:** High
- **Code:**
  ```js
  previewTournament.preferences.cochonettesEnabled && game.score_history && game.score_history.length;
  ```
- **Issue:** No optional chaining on `preferences`. Older tournaments lack this field.
- **Scenario:** Viewing an archived tournament created before the cochonettes feature crashes the Results component.

### 7. Computed mutates reactive source data

- **File:** `src/components/partials/TeamsList.vue:446`
- **Severity:** High
- **Code:**
  ```js
  group.forEach((team) => {
    team.wins = teamWins[team.title] || 0;
    team.pointsPlus = teamPointsPlus[team.title] || 0;
    team.pointsMinus = teamPointsMinus[team.title] || 0;
  });
  ```
- **Issue:** Computed property `sortedGroups` writes directly to reactive source objects. This can trigger infinite re-computation loops or stale cached values.
- **Scenario:** Groups system tournament — the computed invalidates itself on every access.

### 8. Crash in restoreRound

- **Scenario:** Admin restores a round on a tournament with imported teams that never played.

### 9. Tab navigation completely broken

### 10. Stored XSS via player names

- **File:** `src/components/tir/TirPublicView.vue:197, 220`
- **Severity:** High
- **Code:**
  ```js
  formatName(name) {
  ```

## Medium — Significant Issues

### 14. gameHasError misses 0-0 draws

- **File:** `src/helpers.js:601-603`
- **Code:**
  ```js
  game.team_1_score && game.team_2_score && game.team_1_score === game.team_2_score;
  ```

- **Scenario:** Both scores entered as 0, no validation warning shown.

### 15. Incomplete game counted in head-to-head

- **File:** `src/helpers.js:38-40`
- **Code:**

  ```js
  if (gameInRound.team_1_score != null || gameInRound.team_2_score != null) {
  ```

## Security Issues

### 25. All tournament data publicly readable

- **File:** `database.rules.json:8`
- **Code:**
  ```json
  "$tid": { ".read": true }
  ```
- **Severity:** Medium
- **Issue:** Any unauthenticated user can read any tournament data if they know/guess UID and tournament ID. IDs are timestamps (predictable).
- **Scenario:** Attacker enumerates tournament IDs and reads all data including team details.

### 26. Scorers get full write access (no role differentiation)

- **File:** `database.rules.json:15-35`
- **Severity:** High
- **Issue:** Rules only check that collaborator entry exists, not whether role is 'admin' vs 'scorer'. A scorer can write to playoff brackets, timers, etc.
- **Scenario:** A scorer uses Firebase REST API to modify playoff brackets or start/end rounds — actions the UI restricts to owners only.

### 27. Email-to-UID mapping exposed

- **File:** `database.rules.json:69`
- **Code:**
  ```json
  "emails": { ".read": "auth != null" }
  ```
- **Severity:** Medium
- **Issue:** Any authenticated user can read all registered email addresses and their UIDs.
- **Scenario:** Malicious user harvests all emails for phishing or enumerates other users' tournament data.

### 28. No data validation rules

- **File:** `database.rules.json` (entire file)
- **Severity:** Medium
- **Issue:** Zero `.validate` rules anywhere. Any authenticated collaborator can write arbitrary JSON shapes to game/score paths.
- **Scenario:** Collaborator writes `{team_1_score: 'NaN', arbitrary: true}` — corrupts tournament state beyond recovery.

### Root causes (shared fixes)

- **No Number() coercion on Firebase scores** — affects items 2, 3, 5, 13, 18, 19. A single utility `toNum(val)` applied at the data layer would fix all.
- **Missing optional chaining / null guards** — affects items 1, 6, 8, 11, 20. Defensive access patterns needed at Firebase data boundaries.
- **No server-side validation** — affects items 26, 27, 28. Firebase rules need `.validate` and role-based write restrictions.
